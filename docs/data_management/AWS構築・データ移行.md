## 5. AWS構築・データ移行

### 5.1 AWS RDSの構築

ローカル環境で構築したPostgreSQLデータベースをクラウド上で管理するため、Amazon RDS for PostgreSQLを構築しました。

AWS RDSを利用することで、データベースサーバーのインフラ管理をAWSに任せながら、PostgreSQLを利用したデータ管理環境を構築しました。

主な構成は以下のとおりです。

| 項目 | 設定 |
|---|---|
| サービス | Amazon RDS |
| データベースエンジン | PostgreSQL |
| DBインスタンスクラス | db.t4g.micro |
| ストレージタイプ | gp3 |
| ストレージ容量 | 20 GiB |
| データベース名 | oa_cartilage_db |
| ポート番号 | 5432 |
| 暗号化 | 有効 |
| ストレージ自動スケーリング | 無効 |

###　使用したAWSサービス

| AWSサービス | 役割 |
|---|---|
| Amazon S3 | 分析結果などのファイルを保管 |
| AWS IAM | AWSリソースへのアクセス権限を管理 |
| Amazon RDS for PostgreSQL | 分析結果を格納するクラウドデータベース |

各サービスの役割を分けることで、ファイルの保管、データベースによる管理、アクセス制御をそれぞれの目的に応じて整理しました。

### 5.2 ネットワーク・セキュリティ設定

ローカル環境からAWS RDSへ接続するため、セキュリティグループを設定しました。

PostgreSQLの接続に使用するTCPポート5432について、接続元IPアドレスを限定したインバウンドルールを設定しました。

また、SSL/TLSを使用してRDSへ接続し、通信の暗号化を確認しました。

これにより、必要な接続元からのみデータベースへ接続できる構成としました。

### 5.3 ローカルデータベースのバックアップ

AWS RDSへの移行前に、ローカルPostgreSQLデータベースのバックアップを取得しました。

バックアップには、PostgreSQLの論理バックアップツールである `pg_dump` を使用しました。

バックアップはカスタム形式で保存し、テーブル構造やデータを含むデータベースの復元に利用できるようにしました。

### 5.4 AWS RDSへのデータ復元

取得したバックアップをAWS RDSへ復元するため、`pg_restore` を使用しました。

復元時には、所有者や権限に関するローカル環境固有の設定を引き継がないようにし、RDS上のデータベースへテーブル構造とデータを復元しました。

また、復元処理でエラーが発生した場合に処理を停止できるよう、エラー時に終了するオプションを指定しました。

### 5.5 データ移行後の検証

データ移行後、AWS RDSへ接続し、テーブル構成とデータ件数を確認しました。

| テーブル名 | レコード数 |
|---|---:|
| samples | 20 |
| pca_coordinates | 20 |
| normalized_counts | 474,200 |
| deseq2_results | 47,420 |
| log2fc_comparison | 23,710 |
| common_significant_genes | 4,445 |
| go_enrichment | 191 |
| **合計** | **550,006** |

移行後の各テーブルのレコード数が、ローカルデータベースの件数と一致することを確認しました。

さらに、DESeq2解析結果からMMP13を検索し、ローカルDBとAWS RDSで主要な解析結果が一致することを確認しました。

これらの検証により、データベースの構造と分析データがAWS RDSへ正常に移行されたことを確認しました。

### 5.6 AWSリソースの運用

本プロジェクトでは、データ移行と検証を実施した後、AWS RDSインスタンスを停止しました。

検証作業を行わない期間はインスタンスを停止することで、継続的な利用を避ける運用としました。

なお、RDSの停止中もストレージなどの料金が発生する場合があるため、利用料金を確認しながら必要に応じてリソースを管理する方針としました。
