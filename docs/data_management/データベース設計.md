## 4. データベース設計

### 4.1 設計概要

本プロジェクトでは、遺伝子発現解析で得られたデータを効率的に管理するため、PostgreSQLを使用してデータベースを設計しました。

データベース名は `oa_cartilage_db` とし、サンプル情報、遺伝子発現データ、統計解析結果、機能解析結果を、それぞれの役割に応じたテーブルに分割して管理しています。

テーブルを分割することで、データの種類ごとに管理しやすくするとともに、SQLによる検索・集計・テーブル間の結合を可能にしました。

### 4.2 テーブル構成

本データベースは、以下の7つのテーブルで構成されています。

| テーブル名 | 役割 |
|---|---|
| `samples` | サンプルの基本情報を管理 |
| `normalized_counts` | 各遺伝子・サンプルの正規化発現量を管理 |
| `pca_coordinates` | PCAによる各サンプルの主成分座標を管理 |
| `deseq2_results` | DESeq2による差次的発現解析結果を管理 |
| `log2fc_comparison` | 解析モデル間のlog2 Fold Change比較結果を管理 |
| `common_significant_genes` | 解析モデル間で共通して有意となった遺伝子を管理 |
| `go_enrichment` | GO enrichment解析結果を管理 |

### 4.3 テーブル間の関係

データベースでは、サンプル情報を中心に、発現データやPCA座標を関連付けています。

` samples ` テーブルには、各サンプルの識別子を主キーとして設定しました。

` normalized_counts ` および ` pca_coordinates ` テーブルでは、サンプル識別子を外部キーとして使用し、` samples ` テーブルのサンプル情報と関連付けています。

これにより、遺伝子発現量やPCA座標を、サンプルのグループ、年齢、性別などの情報と組み合わせて検索できる構造としました。

### 4.4 主キー・外部キーによるデータ管理

主キー（Primary Key）は、テーブル内の各レコードを一意に識別するために使用します。

外部キー（Foreign Key）は、他のテーブルの主キーなどを参照することで、テーブル間の関連性を定義します。

本プロジェクトでは、サンプル情報を基準として発現データやPCA座標を関連付けることで、サンプル識別子の不一致や、存在しないサンプルに紐づくデータの登録を防ぐ構造としました。

### 4.5 SQLによるデータ検索・集計

データベースに格納した分析結果は、SQLを使用して検索・集計できるようにしました。

例えば、正規化発現量とサンプル情報を結合することで、特定の遺伝子についてNormal群とOA群の発現量を比較できます。

また、DESeq2の解析結果と発現量を組み合わせることで、統計解析結果と実際の発現量を同時に確認できるようにしました。

このように、分析結果をデータベース化することで、CSVファイルを個別に開くことなく、必要なデータを検索・比較できる構成としました。
